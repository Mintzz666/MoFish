二、产品方向和架构

- 名称始终 MoFish，定位轻松休息的电子鱼缸；先把一个人养鱼和布景的体验做好。
- 保留游客、本地存档、离线能力、导入导出、无签到要求、无饿死惩罚。
- 保留独立 Cloudflare 静态入口 + Supabase Auth/Postgres；不依赖 ChatGPT 登录。
- 不引入 D1 第二权威数据库、自管常驻服务器、付费素材/服务或复杂账号系统。
- 小步分离领域状态、存储/同步与 renderer。Three.js 可用于 3D；不重写已经验收的认证。
- 2D 与 3D 操作同一份领域存档；视觉切换不丢数据，WebGL 不可用时保留可玩的 2D。
- 为未来多人保留清晰的数据接口和对象 ID 即可；不要提前实现成员表、邀请、角色、操作日志系统或共享 UI。
- 如新增造景字段/存档版本涉及服务端校验，提交新的版本化迁移和兼容方案；
  不改已应用的 A 迁移，不削弱 RLS/owner 授权，不给浏览器直接写表权限。
  前后端均校验持久对象的 ID、数量、坐标/旋转/缩放边界，旧客户端不能静默丢弃新版造景。

三、阶段 B：单人完整体验（原 C + D 合并）

目标是看得出提升、可长期使用的立体鱼缸，不只给 2D 图形加透视或把刚性鱼模型平移。

设计默认方向：
- 审美关键词：清新、高级、自然、通透、安静、放松。默认走精致自然水族景观，而非夸张卡通或游戏战斗 HUD；鱼缸为主角，工具少打扰。
- 页面采用暖白/浅灰背景、克制的薄荷/青绿点缀、清晰文字层级与留白；水下采用清透的青绿、自然砂石、水草层次，鱼有少量柔和暖色亮点。
- 高级感通过形态比例、材质、光照、构图与细节统一实现；避免高饱和荧光、大面积炫光、过度玻璃模糊和密集浮层。
- 默认场景应有前中后景、高低错落、视觉焦点和鱼游动的留白；随机变化在统一配色/材质范围内，不能杂乱堆满。
- 重新整理电脑与手机布局、账户/存档入口、喂食、选鱼、造景、状态提示与反馈。
- 核心操作在手机上可完成，不依赖 hover；交互可取消，加载、出错、离线/冲突状态清楚。
- 明确键盘操作和可读文字，对比度、触控命中区和减少动态效果可用。

先做可运行的设计/3D 原型与电脑、手机截图并提交，形成可反馈节点。
本长任务默认授权沿上述既定风格继续细化实现，无需为颜色、间距等常规选择暂停整个任务；
若收到用户方向反馈及时整合。涉及明显改变产品定位、付费依赖或破坏旧存档时再提出具体问题。
这将旧 C 的“先等设计方向反馈”改为有明确默认方向的原型检查点，不意味着设计已获最终验收。

必须实现：
1. 真正 Three.js/WebGL 3D 鱼缸、可辨识鱼体、相机、光照和景深层次；限制相机范围，
   桌面和触控可操作，避免穿模和丢失鱼缸。选择/点鱼/喂食不因 3D 坐标转换失效。
2. 鱼有连续身体到尾部的相位摆动、转弯弯曲、加减速、自然巡游、边界与基础障碍避让、追食。
   行为参数随鱼种或体型有差异；避免随机瞬移、频繁抖向、持续穿墙。无需昂贵流体或物理锁步。
3. 水面波动/光影、水下层次与适量焦散、随水摆动的水草；效果应能在目标设备稳定运行。
4. 可编辑并持久保存的造景最小闭环：水草、石块、沉木等少量可再分发物件；
   添加、选择、移动、旋转、删除；使用鱼缸本地/归一化坐标，校验边界和对象 ID，
   布局刷新、同账号换设备能恢复。不要扩展为无限素材商城或复杂地形编辑器。
5. 延续 A 的单用户跨设备云存档：同步鱼的身份、名字、成长、喂食及持久布局；
   瞬时位置、尾摆、水波和相机由本机计算，不逐帧写数据库。
   同账号两个设备同时编辑造景仍用原子 revision 和显式冲突/备份，不能静默覆盖。
6. 旧 version:1 存档可无损读取/升级；迁移前留备份，补充字段有合理默认，坏数据不能破坏原档。
   明确新增造景在 2D 的简化显示与导出/导入行为；不能要求用户清浏览器数据才能升级。
7. 2D/3D 切换及 WebGL 不可用、context lost 或资源加载失败时可恢复/降级，账号和存档仍可操作。
   后台暂停动画、减少动态效果、至少低/高画质档，清理旧场景 GPU 资源，防止反复切换渲染器或重建场景后持续涨内存。
8. 所有模型、贴图、字体、音效记录来源和许可证；可用自制程序化模型。
   新依赖与素材随构建可部署，遵守 CSP；不能临时关闭 TLS/CSP 或依赖不稳定远端素材来交差。

用户补充需求的详细交付标准（与以上要求同时生效）：

3.1 多种鱼体与个体差异
- 默认交付至少 8 种轮廓明显不同的鱼型。具体鱼种、名称、体态、鳍尾结构、花纹与四阶段外形由 Hermes 自主设计，
  形成统一风格的类型目录，不预设必须照着制作的鱼型清单；不强求生物学仿真。
  差异必须体现在体型比例、头腹尾轮廓、鳍形或游姿，不能只复用同一网格换六个颜色。
- 用户可选择鱼型添加，也可使用随机添加；随机从受控鱼型/配色中选取，不强迫用户每次都接受随机结果。
- 同一种鱼明确支持随机颜色：Hermes 设计协调的色域/调色板、主辅色与花纹组合，
  在创建个体时生成并保存，不把颜色固定为每种鱼一个色值。同型个体还可有适度体长/体宽、鳍比例与游动节律差异；
  色彩和形态仍能辨认鱼型，避免畸形几何或随机荧光杂色。成长可在已有个体配色基础上渐进显色，不重掷颜色。
- 形态影响运动表现：短身、长鳍、细长鱼的摆尾幅度/频率、转弯和巡游节奏有区别，鳍尾连续变形。
  成长需按下方四阶段新规则完善，体型变化自然；保留 A 的无饿死、服务端权威和 24 小时离线成长上限，
  本次允许调整成长速度与喂食成长贡献，必须版本化说明并保留旧鱼进度。
- 使用当前 4 种旧 species 索引的明确兼容映射，保留鱼 ID、名字、种类语义、成长和喂食记录；
  不因重排新鱼种目录使已有鱼突然变成另一种。稳定类型 ID 与旧档映射应有测试和文档。

3.2 多样水草、石头与造景随机性
- 默认至少 6 类轮廓/结构不同的水草，具体品类、叶型、株形与组合交给 Hermes 自主设计；
  各类有长度、叶宽/数量、分枝、弯曲和色调的受控随机差异，摆动柔和且不全体同步。
- 默认至少 5 类明显不同的石型，具体轮廓、岩面、层理、色系与材质交给 Hermes 自主设计；
  同类通过轮廓、尺度比例、表面起伏、色差和粗糙度产生个体变化，不只是缩放同一块石头。
- 保留沉木类造景，与砂底/水草/石头在材质和比例上统一；无需海量资产库。
- 添加物件时生成随机个体预览；用户可显式“换个造型”再确认。已有物件不能刷新后自行换形。
- 初始/推荐构图可随机生成少量布局变体，但首次创建后固定，后续进入/切画质不自动重排；
  如提供整缸重新随机布景，必须显式触发、预览确认或可撤销，保留已有鱼和已保存存档。
- 控制随机参数范围、物件数量、可用游动空间和碰撞体；随机大石/水草不能封死鱼群或盖住全部视野。

3.3 用户可移动水草、石头与沉木
- 提供清楚的“观赏/布景”模式。观赏时点水面喂食、点鱼查看；布景时点选物件并高亮，
  拖动改变底面位置；鼠标、触控和相机手势有明确分工，拖石头不能同时喂鱼/转相机。
- 支持选中后的旋转、有限等比缩放、删除、取消本次操作/撤销最近一次编辑；
  手机有可点按的微调/旋转/尺寸控件，键盘可完成基本选择和移动，不能只在桌面拖拽可用。
- 移动可在前后/左右方向进行，有落点预览/边界反馈；石头落底，水草根部锚定底面，
  不随机悬浮、不穿出缸体。物件间允许自然组合重叠，但避免严重穿插或选中后无法取回。
- 显式确认或拖动结束后保存最终变换，本地编辑过程可落盘保障恢复；
  不逐 pointermove 发云请求，仍保留同步去抖/冲突与未同步副本。
- 碰撞/避障数据随布局更新，移动后鱼不持续穿过大石；极端布局能恢复合理位置。

3.4 在用户设备本地渲染的光影与材质
- 使用浏览器 WebGL/Three.js 和本机 GPU 实时渲染；“利用本地资源”指用户设备算力与随应用提供的资源，
  不依赖远程渲染服务器、云 GPU、外部 AI 每帧生成或读取用户任意磁盘文件。
- 模型/贴图/shader 可程序化生成或使用有许可证的资源，随构建同源发布；
  首次加载后的离线能力按缓存策略验证，不能仅开发机本地路径存在而部署后丢资源。
- 高画质做清楚的层次：柔和主光与环境补光、鱼/水草受光、石头接触阴影/遮蔽、
  水面细波高光与水下焦散，合理的颜色空间/色调映射和表面粗糙度。
- 水与玻璃要通透，反射/折射近似可接受；避免透明排序错误、闪烁、过曝、全缸灰雾和镜面挡鱼。
  不强求光追或昂贵流体解算；可组合实时 shader、轻量阴影和预计算资源达到整体效果。
- 保留日/夜切换，夜间柔和、鱼草仍可见；默认无频闪、快速闪光或炫目 bloom。
- 优先桌面较高质量，手机按能力限制像素比、阴影分辨率、后处理和可见细节，可手动低/高画质。
  动态调质量要平滑；相同物件在不同档位保留身份、主体轮廓与位置，不能以重新随机生成冒充降级。
- 限制不必要的每帧 CPU 分配和 GPU 负担，可使用共享材质、实例化、LOD；
  明确纹理/几何/材质销毁，后台暂停，恢复时不累积大量时间步造成鱼瞬移。

3.5 随机外观、布局与旧档的持久化
- 为每条鱼和每个造景保存稳定 ID、类型、外观 seed/必要参数及生成器版本；鱼的随机主辅色/花纹也属于持久外观；
  布景保存鱼缸本地位置、旋转与缩放。生成器升级必须保留旧算法或迁移为固定参数，不能使旧外观悄悄重掷。
- 不能只在渲染器里 Math.random() 后丢弃结果；刷新、导出导入、2D/3D 切换和同账号跨设备
  恢复后应是同一条鱼、同一株草/石头、同一份布局。跨设备画质不同允许细节简化，不允许对象变形态。
- 动画相位和瞬时游动可各端不同，不要求像素一致；持久外观与布景一致性应可单独验证。
- A 的 plants 是数量字段，需将旧数量稳定迁移为新对象列表（含合法坐标和稳定 seed），
  旧档升级不能每次产生新水草或修改原鱼身份。校验器/序列化/canonicalState/缓存/备份/导出及
  服务端 RPC 必须一起支持新字段，避免前端 validator 丢字段，或单纯视觉变化触发无变化云端上传。

3.6 每条鱼的年龄、四阶段成长与实际进食
- 每条鱼独立成长，四个阶段命名为“鱼苗期 → 幼鱼期 → 亚成年期 → 成年期”，UI 显示鱼龄、阶段与进度。
  鱼龄是自出生时间以来的日龄，成长阶段由累计成长值决定，两者不能混为一个字段。
- 保留可迁移的 growth 进度区间，默认建议阈值 0.15 / 0.4 / 0.7，依次对应四阶段；
  成年仍从 0.7 起，旧成年鱼不能因加阶段倒退。阈值集中配置，Hermes 结合体态曲线校准并解释旧档影响。
- 成长同时来自实际经过的服务端时间和实际吃到的食物量；喂食按钮点击次数不直接算进食。
  食物没被吃到不增加成长，多条鱼按各自吃到的数量记账，不能一次喂食让所有鱼都满额成长。
- 速度默认建议：持续每日照料的自然成长约 14 天到成年，正常进食可缩短到约 10 天。
  建议起始参数自然 growth +0.05/24h，营养成长最多 +0.02/24h；具体每份食物收益、
  份数阈值与日窗口/滚动窗口由 Hermes 在规则表明确，实测验证后可校准但必须说明。
  这些是默认体验参数，不是要求用户真实等 14 天验收；超过 24 小时离线的时间按既有限额处理，
  所以上述天数是正常周期登录/照料下的目标，不承诺长期离线也同速成长。
- 给喂食成长设置服务端数量/时间窗口上限，避免连续点几百次立即成年；表现可提示“已经吃饱”，
  不新增强制签到、饥饿死亡、惩罚性掉级或长时间不来就退化。正常不喂食仍能随时间成长。
- 四阶段视觉变化由 Hermes 按鱼型设计：鱼苗小且幼态，幼鱼逐渐长大，亚成年鳍/比例/花纹更完整，
  成年达到该鱼型稳定体态。每个阶段要有可辨认差异，同时体型、鳍和显色连续过渡，
  不在阈值处突然瞬移放大或换成另一种鱼。
  可基于同一套参数化模型做连续变形/缩放，无需为每条鱼准备四份完全独立模型；
  但不能只有文字阶段改变、鱼体大小完全一样，也不能只做四个颜色贴片。
- 鱼种之间成年尺寸与体态有区别，大小受鱼缸游动空间和碰撞体约束；
  成长改变体型后同步更新选取/避障半径，避免成年鱼穿墙或挤成一团。
